# Parity harness

Proves a page behaves the same before and after a change. Used in the audit to check the Leads and Staff refactors (every DOM snapshot, API call, toast and dialog matched).

- `LeadsOld.jsx`, `StaffOld.jsx`: the **exact original** pages from the old repo (`update` @ 8ccb1a5). In git tag `frontend-original` these two pages are the audit refactor, so these copies are the true originals.
- `parity.test.jsx`: renders the old and the new page through the same scripted session with a mocked API and compares them.

To use it for a restyle:
1. Copy the harness and the original page into `frontend/src/__parity__/` (the original page keeps the same relative imports as `pages/`).
2. Compare **text, roles, labels, API calls, toasts and dialogs**, not class names: in `canon()` drop the `class` attribute, because a restyle changes classes on purpose.
3. Run `npx vitest run src/__parity__`, then delete the folder (it is not part of the app).

## Known, intended differences from the originals
These are changes the build plan asked for, so a parity run should expect them and not count them as regressions:
- **Sign-in codes removed (D5, item 0.6).** `Login.jsx` has no code-entry step, `StaffAccessModal.jsx` has no "Sign-in code by SMS" switch, and the Staff action "Access & permissions" now reads "What they can see and do." (`StaffOld.jsx` still ends with ", and sign-in codes.").
- **Staff wired to the new server (item 1.1).** The new server issues passwords, so `Staff.jsx` has no Password field: a new account shows its one-time password once (the same sheet as "Reset password"), and an edit changes the PIN but not the password. A new account asks for a **Username** (2 to 32 characters, permanent). Each row shows the username under the name. Email stays required on the form, as before. The staff adapter refuses a typed password with a message instead of dropping it. `StaffAccessModal.jsx` lost a comment about sign-in codes.
- **Leads wired to the new server (item 1.2).** The server's pipeline is new, contacted, qualified, converted, lost, so: "Rescheduled" and its follow-up date are gone (there is a "Qualified" step instead); "Cancelled" is the server's `lost` and asks why; the source list drops "referral" (files as other) and adds phone and website; the form's email is added to the lead's notes (the server has no email field); a repeat enquiry from a phone that already has an open lead says so instead of looking like a new lead. A call, message, meeting or note logged on a lead is stored as a message (a meeting is a note starting "Meeting: "). **Convert to order** sends payment type and city in the order's notes, and adding to an existing order is not offered (the server refuses a second active order for a phone). `productsApi.list` now works for the product pickers; the rest of `productsApi` waits for item 2.2.
- **Security wired to the new server (item 1.3).** The devices list, "Sign out device" and "Sign out all others" needed no change, and the sign-in rules editor works as before. **Recent security events** now lists lockouts, wrong passwords, resets, role and access changes and similar lines from the audit trail (`GET /api/security/events`, admins only), plus refunds, voids and stock changes at or over the limits saved on this page. Those rows have no address except a reused sign-in. Nothing raises the alert limits as a notification yet; they only decide which lines are listed.
- **Attendance wired to the new server (item 1.4).** Clock in and clock out work as before, and a second clock-in the same day, or a clock-out with nothing open, shows the server's reason. The team table is now "Today · team" and lists every active staff account (the new server has no telesales group), and someone a manager marked absent shows their reason. Not on the new server yet, so not offered: a handover note on clock-out and the "before you go" summary (with the shift widget, 2.4), and "Run reassignment now" with its sentence about automatic reassignment (4.6). The new `GET /api/payroll/attendance/today` (people who may see the team) feeds the table. Recording an absence is still a server call with no screen.
- **Payroll wired to the new server (item 1.5).** The Payroll page (one person's pay for a period, and recording a loss deduction) reads `/api/payroll/staff/:username`. Differences: a person with **no pay profile** for the period gets the server's message instead of a summary, because pay profiles (retainer, commission plan, fees) must exist first and have no screen yet; **bonuses** now show as their own lines (the server has them, the old page did not); a loss deduction **needs a reason**, and is filed on today's date in shop time (East Africa Time); if a locked payroll run covers exactly the period, the page shows that run's frozen figures and says so. Pay runs, approval, payment, payslips and the CSV are server features with no screen in this page, so they are not part of item 1.5.
- **Error messages show the reasons.** When the server refuses a request with a list of reasons (`details`), `getErrorMessage` now appends up to three of them, so a screen says "The end cannot be before the start." instead of only "Some fields are missing or not valid." Every screen benefits.
- **Orders: making an order by hand and pulling online orders (item 1.6).** `ordersApi.create` takes `{ customer_name, customer_phone, items, discount, notes, assigned_staff_id }` (items by product id, or with their own code, name and price; money in cents) and answers with the order. A phone that already has an active order is refused with the server's message, and that order's reference is in the error's details. No screen calls `create` yet; the New order screen is part of Phase 2. **Pull online orders** lists the stores that can be pulled from and pulls from one: orders the server keeps for a person to look at are counted with the ones that could not be added, and the box explains them. Cancelled-in-store orders that cannot be cancelled here (money paid, or already out for delivery) are explained in the same box.
- **Order search by phone number** now finds an order however the number is typed (0712 345 678, +254 712 345 678, or the last digits). Before, a full local number found nothing, because phones are stored as their last nine digits.
- **Settings > Messaging wired to the new server (item 1.7).** The customer SMS card (credentials, test message, what is sent and how it is worded, recent messages with retry) and "How customers pay" (paybill number and account prefix) read `/api/sms/*`. The options need a server route that did not exist, so `GET` and `PUT /api/sms/settings` were added (anyone who sees messages can read, administrators change, with the password re-check, each change in the audit trail). `settingsApi` therefore knows **only these eight settings** on the new server: a save that includes any other setting (business name, currency, shop hours and so on, which are item 4.1) is refused whole with a message, so nothing is half saved. Times in the recent-messages table are shown in the form the page already reads. The paybill number must be 5 to 10 digits, the catalog link must start with http:// or https://. **Web-form lead routing** (the next card on that page) has no module on the new server, so it says so; it belongs with the integrations work.
